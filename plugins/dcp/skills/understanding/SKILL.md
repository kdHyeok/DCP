# DCP 이해도 확인

기능을 구현한 뒤 사용자가 구현 방식을 이해하도록 돕는다. 질문과 설명은 사용자의 언어로 한다.
이 절차는 사용자의 작업 요청을 대체하지 않는다. 구현과 필요한 검증을 먼저 마치고 이해를 확인한다.

## 시작 조건

- 사용자에게 요청받은 기능 구현, 버그 수정, 리팩터링의 한 작업 단위를 완료했을 때 항상 시작한다.
- 파일 편집이나 도구 호출 하나마다 질문하지 않는다. 완료되지 않은 구현이나 실패한 검증을 완료로 포장하지 않는다.
- 조사, 계획, 단순 설명, 문서만 고친 작업에는 자동으로 시작하지 않는다. 사용자가 원하면 확인한다.
- 사용자가 이번 확인을 건너뛰거나 그만하라고 하면 현재 확인만 종료한다. 다음 구현을 마치면 다시 확인한다.
- 사용자가 이해도 확인 기능 자체를 끄라고 했다면 이전 대화의 비활성화 요청도 존중한다. 다시 켜 달라는 요청이 오기 전까지 자동 질문하지 않는다.

## 대화 절차

1. **질문한다.** 무엇을 구현했고 어떻게 확인했는지 짧게 알린 뒤, 방금 구현한 핵심 동작에 대한 질문을 하나 한다. 먼저 정답을 설명하지 않는다. 단순히 "이해했나요?"라고 묻지 않는다.
   - 예: "이 요청이 들어오면 어떤 함수들을 거쳐 결과가 만들어지는지 자기 말로 설명해 주세요."
   - 예: "이 검증을 빼면 어떤 입력에서 문제가 생길까요?"
   - 예: "여기서 이 방식을 선택한 이유는 무엇일까요?"
   - 질문은 실제 변경한 코드에 근거하고, 아직 가르치지 않은 주변 지식이나 문법 암기를 시험하지 않는다.
2. **기다린다.** 질문을 응답의 마지막에 두고 턴을 끝낸다. 사용자 답변 전에는 다음 기능을 구현하거나 이해 확인을 완료 처리하지 않는다. 시간 경과나 무응답을 이해의 증거로 삼지 않는다.
3. **답변을 판단한다.** 다음 사용자 메시지를 대기 중인 질문과 연결해 읽는다. 정답과 표현이 같을 필요는 없다. 핵심 동작과 이유를 자기 말로 맞게 설명하거나 올바른 결과를 근거와 함께 예측하면 충분하다. "네", "알겠어"만으로 이해를 입증했다고 판단하지 말고 짧은 확인 질문을 하나 한다. 단, 사용자가 명시적으로 건너뛰면 그 요청을 따른다.
4. **이해했으면 마친다.** 답변에서 맞게 이해한 핵심을 한 문장으로 짚고 확인을 종료한다. 불필요한 추가 시험을 이어가지 않는다. 후속 작업은 사용자가 이미 요청한 범위에서만 진행한다.
5. **부족하면 쉽게 설명한다.** 맞는 부분은 인정하고 빠지거나 틀린 부분만 설명한다. 쉬운 말과 실제 코드 흐름, 작은 입력·출력 예시를 우선하고 필요할 때 비유를 쓴다. 비유는 실제 동작과 연결한다. 이어서 같은 개념을 다른 예제로 확인하는 질문 하나를 하고 다시 기다린다. 정답을 설명한 문장을 그대로 따라 말하게 하지 않는다.
6. **반복한다.** 이해가 확인될 때까지 설명과 재질문을 반복하되 사용자의 중단·건너뛰기 요청을 존중한다. 주제를 바꾸라는 요청이면 미확인 상태임을 짧게 알리고 새 요청을 따른다.

대기 중인 구현, 질문, 확인한 내용은 현재 대화와 대화 요약에서 이어 간다. 문맥이 사라졌다면 이해했다고 추측하지 말고 확인할 구현을 다시 정한다.
사용자 답변을 채점하기 위해 파일을 쓰거나 외부 서비스에 전송하지 않는다. 이 스킬은 코드 정확성 검증이나 테스트를 대신하지 않는다.
